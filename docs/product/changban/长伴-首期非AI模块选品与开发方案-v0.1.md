## 0. 关于「从粉丝留言里找」

留言数据在你们的公众号/社群/评论后台，本方案无法直接读取。建议按下面两条走：

1. **先按本方案的候选池与 P0 组合开工**（不阻塞开发）；
2. **回填 50–200 条真实留言**（原文粘贴或 Excel），我用第 2 章的打分表重排一次，把假设替换成数据结论。

判断一条留言值不值得做，先看句式，命中率很高：

- 「能不能加个……」「要是能……就好了」→ 明确功能诉求
- 「我每天都在……」「每次都要……」→ 高频刚需
- 「求一个……」「有没有……」→ 有搜索意愿，可做流量入口
- 只有情绪没有场景（「希望更好用」）→ 暂时丢弃

## 1. 为什么首期先做非 AI 模块

不是降级，是三步棋：

| 理由 | 说明 |
| --- | --- |
| **合规先行** | 生成式 AI 备案周期不可控；非 AI 模块不涉及，可以先上线、先验证留存 |
| **留存打底** | AI 对话是用完即走，工具模块给用户「每天打开一次」的理由 |
| **稳定性兜底** | 全部离线可用；模型故障时产品依然完整可用，兑现「稳定可靠」 |
| **数据资产** | 纪念日、打卡、待办沉淀为用户数据，换 App 成本变高 |
| **成本极低** | 零 token 成本，边际成本接近 0，适合冷启动 |

对应到产品叙事：**AI 负责惊喜，工具负责日常。** 两者缺一，留存都立不住。

## 2. 选品框架：五个筛子 + 一条红线

每条诉求按 1–5 分打分，满分 25：

| 维度 | 5 分标准 | 1 分标准 |
| --- | --- | --- |
| 频次 | 留言中多次出现，且是通用诉求 | 个例、小众 |
| 刚需度 | 不解决会明显难受 | 只是新鲜 |
| 无模型可行 | 规则/本地算法可满足 90% 以上 | 必须理解自然语言 |
| 轻量 | 两步内完成核心动作 | 需要多层表单 |
| 沉淀 | 产生长期用户数据 | 用完即走、无数据 |

**排序规则**：总分 ≥ 18 进 P0；14–17 进 P1；< 14 观察。

**一票否决红线**：医疗诊断、金融投资建议、涉政内容、需要专用资质的类目（如医疗健康、金融）。分数再高也不进首期。

## 4. 首期 P0：五件套

选它们的逻辑：**四个是「每天打开的理由」，一个是「搜索流量的入口」，全部零模型、零 token、可离线。**

### 4.1 倒数日

- 功能：新建事件（名称、日期、重复、颜色）→ 首页卡片显示「还有 N 天」→ 列表排序 → 生成分享图（canvas）。
- 细节：支持「正数 / 倒数」双向；支持「已过 N 天」（纪念日场景）。
- 数据：本地 + 登录后云同步。
- 成功指标：创建率、7 日回访率。

### 4.2 今日待办

- 功能：快速添加、今日/全部切换、勾选完成、左滑删除、可选四象限。
- 非 AI 亮点：**粘贴多行文本自动拆成多条**（按换行/分号规则拆分），体验接近 AI，实现零模型。
- 数据：云同步；本地缓存 + 离线队列。
- 成功指标：人均日新增条数、完成率。

### 4.3 专注计时

- 功能：25 / 45 / 60 分钟预设、3 种白噪音、结束提示、专注记录与周视图。
- 关键实现：记录 `startAt` 时间戳，回到前台重算剩余时间；**不要依赖 setInterval**。
- 数据：专注记录上云，白噪音音频走 CDN。
- 成功指标：周使用次数、平均时长。

### 4.4 习惯打卡

- 功能：建习惯（每天 / 每周 N 次）、一键打卡、连续天数、月度热力图、每月 3 次补卡。
- 关键实现：打卡按「本地日期」判定，避免跨时区错乱；提醒走订阅消息。
- 数据：云同步。
- 成功指标：连续 7 天打卡用户占比。

### 4.5 随身工具箱

6 个小工具合一，纯本地计算：

| 工具 | 说明 |
| --- | --- |
| 文本统计 | 字数、字符数、行数、阅读时长 |
| 文本处理 | 大小写、去重、排序、去空行 |
| 单位换算 | 长度/重量/面积/温度/数据 |
| 时间戳转换 | Unix ↔ 日期，支持毫秒 |
| 二维码生成 | 本地 canvas 绘制，可保存 |
| 随机数 / 密码 | 指定位数的随机字符串与密码 |

- 价值：承接「单位换算」「二维码」等搜索词，几乎零维护。
- 注意：工具箱内部用二级列表，不占首页卡片位（作为一个模块卡片进入）。

## 5. 与现有模块体系的对接（含一处原则修正）

### 5.1 注册表字段取值

| 字段 | 非 AI 模块取值 |
| --- | --- |
| type | tool / view |
| prompt_ref | null |
| tools | [] |
| model_policy | none |
| offline | true |
| storage | local + cloud（登录后同步） |
| tier | 免费 |
| min_client | 1.0.0 |

### 5.2 原则修正（重要）

原方案写「所有模块最终都收敛到对话」。加入非 AI 模块后，修正为：

> **AI 能力统一收敛到对话；非 AI 工具以轻页面承载，但共用同一套模块卡片、视觉规范与入口。**

- 首页仍是唯一入口，对话仍是默认落点；
- 工具/视图模块打开后是独立轻页面，顶部保留「用对话继续 →」入口，可把当前内容带进对话；
- 仍然**不做**每个工具一个 Tab。

这样既保住了「简单」，也不硬把计时器塞进聊天框。

## 6. 三个必踩的工程坑

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| 后台计时失效 | 切后台后计时器停摆、回来时间不对 | 只存 `startAt` 时间戳，`onShow` 时重算；结束提醒用订阅消息补 |
| 订阅消息授权 | 一次性订阅一次只能发一条，打扰多了用户拒绝 | 在「创建提醒」当下引导授权，按需多次；长期提醒改为「进小程序时补发提醒卡」 |
| 本地存储上限 | 单 key 1MB、总计 10MB，打卡记录很快撑满 | 记录类数据存云数据库，本地只做缓存；离线写入队列，联网补同步 |
| 包体超限 | 白噪音、词库、图标把主包撑爆 | 静态资源走 CDN 或分包，主包守住 2MB，发布前做包体门禁 |

## 7. 开发排期（3–4 周）

| 周 | 内容 |
| --- | --- |
| W1 | 模块框架 + 倒数日 + 工具箱（最小闭环，可内测） |
| W2 | 待办 + 打卡（含云同步与离线队列） |
| W3 | 专注计时 + 白噪音 + 订阅消息 |
| W4 | 联调、性能与包体、提审与灰度 |

**人力**：小程序 2、后端 1、设计 0.5、测试 0.5。P0 合计约 17 人日 + 框架 3 人日 + 联调 4 人日。

**更保守的切法**：先上「工具箱 + 倒数日」（约 1 周），验证入口与留存，再补待办/打卡/计时。
